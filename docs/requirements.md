# RUN TERRITORY 요구사항 분석

## 1. 프로젝트 목표

RUN TERRITORY는 사용자가 실제 러닝을 통해 GPS 경로를 기록하고, 폐곡선으로 만든 면적을 영토로 등록하는 위치 기반 러닝 게임이다.

사용자는 러닝을 통해 포인트를 얻고, 포인트로 캐릭터 뽑기와 강화를 진행하며, 점령 면적과 누적 거리 랭킹을 통해 지속적인 참여를 유도한다.

---

## 2. 핵심 기능 요약

1. Firebase 기반 로그인/회원가입
2. GPS 러닝 경로 기록
3. 폐곡선 완성 시 면적 계산 및 영토 등록
4. 러닝 결과에 따른 포인트 지급
5. 포인트 기반 캐릭터 뽑기 및 강화
6. 영토 침략 및 점령률 변화
7. 영토 자연 감소
8. 면적/거리 랭킹 제공

---

## 3. 사용자 흐름

1. 사용자는 Firebase Auth로 로그인 또는 회원가입한다.
2. 앱은 Firebase ID Token을 서버에 전달한다.
3. 서버는 토큰을 검증하고 사용자 정보를 생성 또는 조회한다.
4. 사용자는 러닝을 시작하고 GPS 경로를 기록한다.
5. 러닝 종료 시 앱은 경로, 거리, 시작 시각을 서버에 전송한다.
6. 서버는 폐곡선 여부, 면적, 포인트를 계산한다.
7. 조건을 만족하면 영토를 등록한다.
8. 사용자는 직접 러닝 보상으로 대표 캐릭터 경험치와 소량의 가챠 재화를 얻는다.
9. 사용자는 획득 재화로 캐릭터를 뽑거나 강화한다.
10. 사용자는 영토와 랭킹을 확인한다.

## 4. 기능별 요구사항

### 4.1 인증 / 사용자

- 사용자는 Firebase Auth를 통해 회원가입할 수 있어야 한다.
- 사용자는 Firebase Auth를 통해 로그인할 수 있어야 한다.
- 서버는 Firebase ID Token을 검증할 수 있어야 한다.
- 최초 로그인 사용자는 `users` 테이블에 자동 생성되어야 한다.
- 최초 로그인 사용자는 기본 캐릭터 1개를 지급받아야 한다.
  - 지급 대상은 common 등급의 공격형/수비형/버프형 캐릭터 중 랜덤 1개다.
- 사용자 닉네임은 필수값이며, 기본값 정책이 필요하다.
  - Firebase `displayName` 우선
  - 없으면 이메일 앞부분 사용
  - Firebase 이메일 정보가 없는 토큰은 인증 실패 처리

### 4.2 GPS 러닝 / 영토

- 사용자는 러닝을 시작하고 종료할 수 있어야 한다.
- 앱은 러닝 중 GPS 좌표를 수집할 수 있어야 한다.
- 러닝 종료 시 앱은 서버에 GPS 경로를 전송해야 한다.
- 서버는 러닝 경로를 저장할 수 있어야 한다.
- 서버는 폐곡선이 완성된 경우 면적을 계산할 수 있어야 한다.
- 계산된 면적은 영토로 등록될 수 있어야 한다.
- 하나의 지도에서 모든 사용자의 영토를 표시할 수 있어야 한다.
- 영토는 개별 ID를 가지며, 캐릭터 배치와 침략 대상 지정에 사용된다.

#### 폐곡선 판단 기준

- 좌표는 `{ lat: number, lng: number }` 형태를 사용한다.
- 좌표가 3개 이상이어야 한다.
- 시작점과 종료점의 거리가 50m 이내이면 폐곡선으로 판단한다.
- 폐곡선이 아니면 러닝 기록은 저장하되 영토는 생성하지 않는다.

### 4.3 포인트 계산

러닝 경로 기반 이동 거리와 평균 페이스를 기준으로 포인트를 지급한다.

폐곡선을 만들지 못한 러닝은 즉시 완주 보상이 더 높을 수 있다. 폐곡선 영토를 만든 사용자는 이후 주기적 포인트 획득이 가능하므로 장기 보상이 더 높아지는 구조를 전제로 한다.

보상을 위해 러닝을 짧게 끊는 행동을 줄이기 위해, 끊지 않고 오래 달린 러닝의 보상은 추가 보정으로 증가할 수 있다.

포인트 공식:

```ts
const basePoints = Math.floor(distanceKm * 100 * paceMultiplier * distanceMultiplier);
const earnedPoints = isClosedLoop ? basePoints : Math.floor(basePoints * 1.3);
```

- `distanceKm`: 서버가 `path` 좌표로 계산한 이동 거리
- `paceMultiplier`: 서버 계산 평균 페이스 기준 보정값
- `distanceMultiplier`: 장거리 러닝 보정값. 현재 구현 기준 `Math.min(1.1 ** distanceKm, 3.0)`
- 폐곡선을 만들지 못한 러닝은 영토를 생성하지 않는 대신 즉시 보상에 1.3배를 적용한다.

| 평균 페이스 | 보정값 |
|---|---:|
| 3분/km 미만 | 무효(0) |
| 3~4분/km | x1.2 |
| 4~5분/km | x1.0 |
| 5~7분/km | x0.8 |
| 7~8분/km | x0.6 |
| 8분/km 초과 | 무효(0) |

앱에서 예상 포인트를 표시하는 경우 서버와 동일한 기준을 사용해야 한다.

### 4.4 캐릭터 / 가챠

- 사용자는 포인트로 캐릭터를 뽑을 수 있어야 한다.
- 사용자는 보유 캐릭터 목록을 조회할 수 있어야 한다.
- 사용자는 포인트를 사용해 캐릭터 스탯을 강화할 수 있어야 한다.
- 캐릭터 등급은 `common`, `rare`, `epic`, `legendary`를 사용한다.
- 캐릭터 타입은 `attack`, `defense`, `buff`를 사용한다.
- 점령형 캐릭터 타입은 사용하지 않는다.
- 100회 뽑기 천장 보장 여부를 기록할 수 있어야 한다.
- 가챠 비용은 현재 구현 기준 1회 100 포인트, 10회 900 포인트를 사용한다.
- 가챠 확률은 현재 구현 기준 common 60%, rare 30%, epic 9%, legendary 1%를 사용한다.
- 캐릭터 강화 비용은 현재 구현 기준 `Math.min(Math.floor(100 * 1.5 ** currentLevel), 5000)`을 사용한다.
- 사용자는 대표 캐릭터를 설정할 수 있어야 한다. 직접 러닝 보상 경험치는 대표 캐릭터에 지급한다.
- 직접 러닝 보상으로 대표 캐릭터 경험치와 소량의 가챠 재화를 지급한다.
- 캐릭터 경험치가 기준치를 넘으면 캐릭터 레벨이 상승하고, 레벨에 따라 캐릭터 능력치가 성장한다.
- 수비형/버프형 캐릭터는 사용자 영토에 배치될 수 있다.
- 캐릭터 배치는 `user_characters.deployed_territory_id`로 특정 영토를 지정한다.
- 하나의 영토에는 하나의 수비형/버프형 캐릭터만 배치할 수 있다.
- 배치 여부는 `deployed_territory_id IS NOT NULL`로 판단하며 별도 `is_deployed` 컬럼은 사용하지 않는다.

### 4.5 영토 침략

- 사용자는 다른 사용자의 영토를 침략할 수 있어야 한다.
- 침략 시 사용할 공격형 사용자 캐릭터를 지정해야 한다.
- 침략 판정에는 현재 사용자의 러닝 로그를 사용해야 한다.
- 침략자는 대상 점령 영토 면적의 최소 30% 이상을 직접 러닝으로 지나가야 침략 전투를 시도할 수 있다.
- 서버는 `POST /territories/:id/attack` 처리 중 러닝 로그의 GPS 경로와 대상 영토의 겹친 면적을 계산해 침략 가능 여부를 판단해야 한다.
- 침략 조건을 만족하면 공격 캐릭터와 대상 영토에 배치된 방어 캐릭터를 기준으로 피해량을 계산한다.
- 피해량은 대상 영토의 점령률 감소량으로 반영한다.
- 감소한 점령률만큼 획득 면적을 계산한다.
- 대상 점령 영토에 포함되지 않은 새 면적은 일반 러닝 영토 생성 규칙에 따라 처리한다.
- 서버는 공격/방어 능력치와 배치 캐릭터 효과를 기준으로 침략 결과를 계산해야 한다.
- 공격력은 `attackerCharacter.character.base_attack + (attackerCharacter.attack_lv - 1) * 5`로 계산한다.
- 방어력은 대상 영토에 배치된 수비형 캐릭터들의 `defender.character.base_defense + (defender.defense_lv - 1) * 5` 합으로 계산한다.
- 실제 방어력은 `defensePower * (occupation_rate / 100)`로 보정한다.
- 최종 피해량은 `Math.max(0, attackPower - defenseWithRate)`로 계산한다.
- 침략 후 점령률은 `Math.max(0, occupation_rate - Math.floor(damage))`로 계산한다.
- 침략 성공 여부는 `occupationRateAfter < territory.occupation_rate`로 실제 점령률이 감소했는지로 판단한다.
- 획득 면적은 `territory.area_sqm * (territory.occupation_rate - occupationRateAfter) / 100`으로 계산한다.
- 하루 침략 가능 횟수는 5회이며, `attack_logs`의 공격자/날짜 기준 카운트로 계산한다.
- 새로 생성된 영토는 약 5분 동안 침략 보호 시간을 둘 수 있다.
- 침략 응답에는 다음 침략 가능 시각과 당일 남은 침략 횟수를 포함한다.
- 현재 쿨타임 미구현 상태에서는 `nextAttackAvailableAt`을 항상 `null`로 반환한다.

### 4.6 영토 자연 감소

- 일정 기간 활동이 없으면 영토 점령률이 감소해야 한다.
- 점령률이 0이 되면 영토는 중립화되어야 한다.
- 점령률은 시간이 지나면 반드시 감소한다.
- 사용자가 요구량만큼 직접 러닝하면 일정 기간 동안 점령률 감소량을 줄일 수 있다.
- 자연 감소 주기와 기본 감소량, 러닝 충족 시 감소 완화량은 추후 확정한다.
- 수비형/버프형 캐릭터가 영토에 배치되는 경우 자연 감소량 또는 감소 주기에 영향을 줄 수 있다.
- 스케줄러 버프 연동 공식은 후속 구현에서 결정한다.

### 4.7 랭킹

- 사용자는 보유 면적 랭킹을 확인할 수 있어야 한다.
- 사용자는 누적 러닝 거리 랭킹을 확인할 수 있어야 한다.

---

## 5. 비기능 요구사항

- `.env`, Firebase Admin 서비스 키, API Key는 GitHub에 커밋하지 않는다.
- 앱과 서버는 동일한 API 명세를 기준으로 개발한다.
- 서버 API는 DTO 기반으로 요청 데이터를 검증한다.
- 앱 연동 전 요청/응답 타입을 명확히 문서화한다.
- 공통 에러 응답 형식을 통일한다.

---

## 6. 앱 연동 전 필수 결정 사항

1. `/running/start` API 필요 여부
2. 침략 쿨타임 적용 여부와 쿨타임 시간
3. 새 영토 침략 보호 시간 저장 방식
4. 버프형 캐릭터의 침략 계산 반영 공식
5. 수비형/버프형 캐릭터의 자연 감소 스케줄러 연동 공식
6. 자연 감소 주기, 기본 감소량, 러닝 충족 시 완화량
7. 장시간 연속 러닝 보상 보정 공식
